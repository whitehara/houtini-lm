# モデル評価記録（OpenRouterバックエンド）

houtini-lmのOpenRouterバックエンドで実際に使われている/検討されたモデルの実測データを集約する場所。
`/mnt/nfs/claude/` 配下の複数の呼び出し元（`plan-reader-lm`エージェント、`lm-delegate`スキルなど）が
それぞれのファイル内にモデル選定の経緯を長々と書くと、呼び出し元自体のコンテキストが肥大化する。
そのため実測データ・比較・結論はここに集約し、呼び出し元は「現在の推奨モデル」と本ファイルへの
リンクだけを持つ。

**運用方針**: 新しいモデルを実測したら、既存の記載は削除・上書きせず追記する（同じモデルの再測定は
新しい日付のエントリとして追加し、古いエントリは残す＝実測条件の変化が追える）。

## モデル別実測データ

### `z-ai/glm-5.3-flash`

- **2026-09-01〜**: `plan-reader-lm`の暫定採用。reasoning強制・既定effort`max`によりレイテンシが重い（4部構成レポート生成で約29秒、タイムアウトで連続失敗した時期あり）
- **2026-09-02〜03、この session 内の実測**: TTFT 5.9秒（trivialな"Reply: OK"）〜24.6秒（`custom_prompt`＋context）〜122.5秒（blob併用の重いタスク）と、タスクの複雑さに応じて大きく変動
- **2026-09-03、フェーズ15クロスレビュー（実運用）**: 非同期化＋ポーリング予算32回/約16分の設計下で、3反復すべて`used`（成功）。ただし各反復ともplannerの収束判定（Step 3）より後に到着したため、判定への採用は0件（構造的な問題であり、モデル性能の問題ではない。詳細は`planner-cross-review`スキルの運用ログ参照）

### `deepseek/deepseek-v4-flash`

- **2026-09-01、lm-delegateでの実機テスト（簡単な関数実装タスク、`max_tokens: 6144`）**: TTFT 2.97秒・合計21秒・reasoningトークン消費ゼロ
- **2026-09-02、`plan-reader-lm`としての実運用（フェーズ14計画立案）**: 反復1は成功したが反復2-3は`call-error`（タイムアウト）。当時は同期または短い待機予算だったため、根本原因はモデルではなくアーキテクチャ（後の非同期化で解消の見込み）
- **2026-09-03、トイベンチマーク（`clampInt`関数1個生成）**: TTFT 4.3秒・総処理10.1秒・reasoning 32%（354/1106トークン）
- **2026-09-03、実ワークロード比較（フェーズ15クロスレビューの3反復プランを`plan-reader-lm`と全く同じinstructionで実測、GLMとの直接比較目的）**:
  - 反復1: TTFT 30.6秒・総処理56.5秒・reasoning 53%（3444/6487トークン）
  - 反復2: TTFT 1.2秒・総処理69.3秒（生成速度43.7 tok/sに低下、houtini-lm側の同時実行枠の混雑が影響した可能性）
  - 反復3: TTFT 29.6秒・総処理47.6秒・reasoning 61%（3410/5624トークン）
  - 平均: TTFT 約20秒・総処理 約58秒
  - **結論: トイベンチマークでの「10倍速い」という印象は実ワークロード規模では再現しなかった**。複雑なタスクでは`mandatory: false`のモデルでも自主的に大きくreasoningを使うため、GLMの実測レンジ（5.9〜122.5秒）と実質的に重なる
  - **品質面の懸念**: 反復3の出力で`src/version.ts`→`src/verson.ts`、`src/suppress-experimental-warnings.ts`→`src/suppress-expermental-warnings.ts`という**ファイル名の転記誤字**を発見。プラン本文を一字一句正確に読み取れるかを見るタスクでこの種の誤りが出るのは軽視できない（同じ3反復で得たGLMの実際のレポートにはこの種の誤字は見られなかった）
  - **この実測に基づき、`plan-reader-lm`のモデル切り替えは見送りと判断**（2026-09-03）

### `moonshotai/kimi-k2.7-code`

- **2026-09-03、トイベンチマーク（`clampInt`関数1個生成、`lm-delegate`のモデル選定調査中）**: TTFT 32.8秒・総処理33.6秒・生成速度1082.8 tok/s（速い）だが**reasoningが942トークン中906トークン（96%）**を占めた
- コード生成特化を謳う（"Best for: complex multi-step tasks, code generation, reasoning chains"）モデルだが、"reasoning chains"の記載通り実際には非常にreasoning重視で、GLM系列と同様の「reasoning強制による重さ」を持つ
- **不採用と判断**（2026-09-03）。生成速度自体は魅力的なため、reasoningを明示的に抑制する手段が判明すれば再検討の余地あり

### `moonshotai/kimi-k2.6`（旧版、2026-09-01時点の記録）

- `max_tokens`未指定時の自動計算値が130,064まで膨らみ（モデル自体の上限235,929は超えないため400エラーにはならない）タイムアウトが発生
- 不採用

### `qwen/qwen3-coder-flash`

- **2026-09-01実測**: OpenRouterのPrivacy/データポリシー設定によりガードレールで弾かれ利用不可（`404: No endpoints available matching your guardrail restrictions and data policy`）
- 仮に利用可能でも`max_completion_tokens`が65,536と狭く、`max_tokens`未指定時の自動計算値が実測で130,019まで膨らむため上限超過（400エラー）のリスクが高いことも判明済み
- ガードレール設定を緩めれば個別に試す余地はある（未実施）

### `openai/gpt-oss-120b`

- **2026-09-01、`plan-reader-lm`のモデル選定調査時**: 直接呼び出しでは高速化を確認（TTFT約2.9秒）したが、reasoning既定effortが`medium`で強制（`mandatory: true`）のため、Agentラッパー経由の呼び出しでは依然タイムアウトが発生
- ユーザーからOllama Cloud運用時の実体験として「gpt-oss:120bは品質が低い」という指摘もあり、`plan-reader-lm`用途では不採用
- **一方、`lm-delegate`経由のi18n翻訳バッチ（tangariaリポジトリ、2026-09-02、82件+85件）では実際に使われ成功**（要修正率2.4%/0%）。用途（翻訳・定型変換）によっては問題にならない可能性がある

### `gpt-oss:20b`（Ollama Cloud時代、参考情報・現在は無効）

- OpenRouter移行前（2026-08-26〜27時点）に`plan-reader-lm`で採用していたモデル。粗い初期案に対する曖昧点検出でhaikuと同数の命中率を示した唯一のOllamaローカルモデルという理由で選定
- OpenRouterバックエンドには直接引き継がれない参考情報

## 集計上の注意

- TTFT・生成速度はhoutini-lmサーバーの負荷（同時実行中の他ジョブ数、`HOUTINI_LM_JOB_CONCURRENCY`既定1の奪い合い）に左右される。単発の実測値を過信しないこと（このファイルの反復2のように、同一モデル・同一タスクでも生成速度が大きくぶれることがある）
- reasoning比率は同一モデルでもタスクの複雑さで大きく変動する（トイベンチマークと実ワークロードで別モデルのように振る舞うことがある。`deepseek/deepseek-v4-flash`の記録を参照）
- ここに記録するのはメタデータ（TTFT・トークン数・reasoning比率・成否）のみ。プラン本文・生成コード片・レポート本文は記録しない
